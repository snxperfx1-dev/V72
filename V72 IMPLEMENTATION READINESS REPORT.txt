REVIEWER'S STANDING ORDERS
Every formula, weight, threshold, and score in the V72 Spec is treated as a hypothesis unless it is directly derivable from existing V71 code. The question being answered is not "Is this design plausible?" but "Is this design correct enough to code today without producing a system that is architecturally sound but empirically wrong?"

PART 2 — ENGINE-BY-ENGINE CLASSIFICATION

ENGINE: ROTATION INTELLIGENCE ENGINE (RIE / Engine 2)
Verdict: APPROVED WITH MODIFICATIONS
What is architecturally correct: The RIE concept is valid and non-threatening to IE1A. All four proposed output variables (rot_pressure, rot_controlStability, rot_transferProbability, rot_state) are new identifiers with no lifecycle authority. The input set (obs_ExpansionScore, obs_DecayScore, obs_AbsorptionScore, efficiency, convexityScore, ede_state, re_resolutionState) is entirely read-only from existing sensors. The IE1A authority boundary is respected — RIE measures pressure, not phase.
Critical flaw — circular dependency risk: The V72 Spec (§3.2) uses re_resolutionState in rot_transferProbability. re_resolutionState depends on ie1a_currentPhase (via re_absorbedAndReturned which reads ie1a_currentPhase). This is not circular — RIE reads re_resolutionState after IE1A computes it — but the execution order in PineScript must be verified. IE1A → EDE → RE → RIE is the required compute order. This order must be explicitly enforced in code placement.
Research items in this engine: The weights in rot_pressure (0.35 / 0.30 / 0.20 / 0.15) and in rot_transferProbability (0.50 / 0.30) are uncalibrated hypotheses. The formula is structurally sound but the constants are invented.
Required modifications before implementation:
1. Weights must be exposed as tunable inputs, not hardcoded.
2. Remove rot_emergingWaveStrength from V1 scope — it overlaps conceptually with rot_pressure and adds calibration complexity without a clear separate downstream consumer. Implement in V2 after rot_pressure is validated.
3. The V72 Spec (§2.2) renames liveDirective to rie_controlDirective. This is incorrect. liveDirective is computed in the Slippage/Opportunity Engine (Section 22 area), not the Rotation Engine. Renaming it would falsely imply RIE owns it. Action: leave liveDirective as-is, move to Advanced display only; do not rebrand it under RIE authority.
Implementation scope: Implement rot_pressure, rot_controlStability, rot_transferProbability, rot_state. Defer rot_emergingWaveStrength.

ENGINE: MULTI-TIMEFRAME CONSENSUS ENGINE (MCE)
Verdict: APPROVED WITH MODIFICATIONS
What is architecturally correct: Extending from 2 HTF levels (tf1, tf2) to a configurable 9-level stack is architecturally clean. V71 already uses request.security() for tf1 and tf2 (lines 286–299). The same pattern extends naturally. The per-timeframe object design (lifecycle progress score, confidence, direction) is non-invasive and derives from existing layer outputs.
Critical flaw — lifecycle progress score mapping: The V72 Spec maps IE1A phases to a 0–100 lifecycle progress integer. This is an architectural overreach if not handled carefully. The mapping assigns cardinal numbers to phases (e.g., Expansion=20, NewHL=80), implying a linear lifecycle progression. IE1A's lifecycle is not linear — it is a conditional state machine. The "progress" score is a display convenience, not a physics measure. It must be labeled explicitly as a display heuristic, not fed back into any decision engine as if it were a continuous lifecycle variable.
Critical flaw — equal-weight TF voting: mce_alignmentScore as a simple count of agreeing TFs gives M1 equal weight to Monthly. This is likely empirically wrong. A Monthly + Weekly + Daily alignment against M1 should outweigh M1's direction. However, the correct weighting scheme is a research question. Therefore:
* Implement structural version (equal weight) first, exposed as a selectable mode.
* Do NOT implement the HTF-biased version as the default until tested.
PineScript constraint — 9 request.security() calls: V71 currently uses 2. Adding 7 more request.security() calls increases compute load significantly. PineScript has a limit of 40 request.security() calls total per script, but performance degrades with many concurrent HTF calls. The Phase 4 roadmap of "9 fully independent TF consensus signals" may hit performance walls. Start with 4 configurable TF inputs (tf1, tf2, tf3, tf4) and extend later.
Required modifications:
1. Implement 4 TF levels in V1 (extend existing tf1/tf2 to tf1/tf2/tf3/tf4).
2. Expose TF weighting as input parameter (equal / linear-HTF-biased).
3. Lifecycle progress map is display-only — never feed numeric lifecycle progress score into decision engines.
4. Rename mce_htfNarrative / mce_mtfNarrative / mce_execNarrative to avoid ambiguity with the Narrative Engine. These are alignment summaries, not narratives. Use mce_htfAlignmentSummary, mce_execAlignmentSummary.

ENGINE: NARRATIVE ENGINE (NE)
Verdict: APPROVED WITH MODIFICATIONS
What is architecturally correct: The single-dominant-narrative constraint is correct and important. The 8 permitted narrative types are well-chosen. Deriving narrative from MCE consensus rather than raw IE1A phase is an upgrade over V71's die_narrativeDir which simply relays ie1a_hypFamily.
Critical flaw — narrative derivation assumes MCE outputs exist: The NE conditions reference mce_htfAlignmentScore. If MCE is not yet implemented (or implements fewer TFs), NE falls back to undefined behavior. The NE must have a graceful degradation path using the existing htfAlign (lines 337–338) as a simplified alignment input when MCE is unavailable.
Specific flaw in narrative conditions: V72 Spec §5.2 "Bullish Continuation" condition: ie1a in {Expansion, NewHL, DemandReturn} with rot_transferProbability < 40. This is partially redundant. Demand Return is a return-to-zone phase — calling it "Continuation" is semantically incorrect. Demand Return should map to "Bullish Pullback" (price returning to demand = pullback in a bull market), not Continuation. This is a semantic classification error that would produce misleading dashboard output.
Required modifications:
1. Fix Demand Return → "Bullish Pullback" (not Continuation). Fix Supply Return → "Bearish Pullback".
2. Add degradation path: if MCE not active, use htfAlign as simplified consensus input.
3. Add ne_narrativeAge counter (bars since narrative last changed) — essential for preventing narrative flapping on boundary conditions.
4. The conflict flag ne_narrativeConflict is correct and important — retain.

ENGINE: TRADE QUALIFICATION ENGINE (TQE)
Verdict: REQUIRES RESEARCH — Implement Structure Only
What is architecturally correct: The TQE concept is correct. A dedicated gate layer between intelligence and decision is architecturally necessary and non-invasive to IE1A. The six input sources (IE1A confidence, ERF confidence, FRZ quality, MCE alignment, RE completion, liquidity) are all real V71 variables.
Why the formula cannot be implemented as written: The specific weights (0.25 / 0.15 / 0.15 / 0.20 / 0.10 / 0.15) and grade thresholds (85 / 72 / 58 / 42) are entirely uncalibrated. There is no empirical basis for these numbers. Implementing them as-is would produce a "grade" that has no validated relationship to actual trade outcomes. A trader given an "A+" signal that systematically produces bad results has been misled by the architecture.
What CAN be implemented now:
1. The TQE structure — the six inputs, the formula skeleton, the output variables.
2. All weights exposed as float inputs with neutral defaults (equal weighting: 0.167 each).
3. The grade thresholds exposed as int inputs with provisional defaults (80/65/50/35).
4. The tqe_readiness boolean gate — the minimum threshold conditions (ie1a_phaseConfidence >= 50, mce_htfAlignmentScore >= 50) are architecturally defensible even without calibration.
5. The tqe_riskLevel logic is defensible: high rot_transferProbability = high risk. This is a structural truth, not a calibrated threshold.
Additional flaw — double-counting: erf_confidence (as calculated at line 1281–1286) already incorporates ie1a_phaseConfidence * 0.40. If ie1a_phaseConfidence is also a direct TQE input at 25% weight, IE1A confidence is counted approximately 1.4× while other components are counted 1×. This must be corrected. Either:
* Reconstruct erf_confidence to exclude the IE1A component (erf_pure_confidence), or
* Reduce the IE1A weight in TQE to 15% when erf_confidence is in the mix.
Required modifications:
1. Expose all weights and thresholds as tunable inputs.
2. Fix the ie1a_phaseConfidence double-counting in erf_confidence.
3. Label the engine output as "Provisional Grade" in dashboard until calibrated.
4. Defer auto-degradation of DOE action based on TQE grade until calibration validates thresholds.

ENGINE: DECISION OUTPUT ENGINE (DOE)
Verdict: APPROVED WITH MODIFICATIONS
What is architecturally correct: The DOE concept is the highest-priority architectural addition. The authority boundary (sole owner of doe_* variables, consumer only, no raw computation) is correct. Resolving the three-directive conflict is mandatory. The output variable set (bias, action, confidence, tradeType, entryMid/High/Low, entryTrigger, entryQuality) is correct and complete.
Critical flaw — premature TQE dependency: doe_action in V72 Spec §12.4 gates on tqe_readiness. If TQE grades are miscalibrated (as established above), DOE inherits those errors. During the calibration period, DOE must have a fallback path that does not depend on TQE grade.
Interim DOE action logic (calibration-safe):


// Phase 1 DOE — uses hard structural gates, not TQE grade
doe_action =
    inv_invalidated ? "No Trade" :
    not te_rrGate ? "Wait" :          // R:R < 1.5 always blocks
    not erf_entryGate ? "Wait" :      // ERF gate (this IS calibrated — §7.2)
    ie1a_currentPhase == "Demand Return" and direction == 1 ? "Long" :
    ie1a_currentPhase == "Supply Return" and direction == -1 ? "Short" :
    "Wait"
// TQE grade used for doe_entryQuality label only — not as action gate — until calibrated
Critical flaw — doe_entryMid derivation uses non-existent variables: V72 Spec §12.7 references frz_bestTop and frz_bestBot. These do not exist. The correct implementation must find the best-score FRZ zone's top and bottom from frz_topArr and frz_botArr at the index where frz_scoreArr is maximized.
Required modifications:
1. Decouple DOE action from TQE grade until calibration complete. TQE grade drives doe_entryQuality display only in Phase 1.
2. Fix frz_bestTop/frz_bestBot references — implement as index-lookup from arrays.
3. The confidence formula (§12.5) is a research hypothesis. In Phase 1, use modelConfidence (already calibrated adaptively) as the primary doe_confidence input, supplemented by mce_alignmentScore and ie1a_phaseConfidence as modifiers.
4. The 88/95 hard caps are arbitrary — expose as inputs.
5. doe_tradeType derivation from ne_dominantNarrative is correct (after NE semantic fix above).

ENGINE: TARGET ENGINE (TE)
Verdict: APPROVED WITH MODIFICATIONS
What is architecturally correct: The three-tier target hierarchy (secondary attractor → TP1, primary attractor → TP2, tertiary → TP3) is architecturally sound and non-invasive. EAE already computes eae_primaryAttractorPrice and eae_secondaryAttractorPrice. Surfacing them as named targets is an integration step, not new computation. The Target Engine converts existing EAE output into trader-readable levels.
Critical flaw — attractor price semantics: After inspecting the V71 code (lines 1231–1260), the attractor price semantics are:
* eae_primaryAttractorPrice when UNRESOLVED = flipBot (bull) or flipTop (bear) — the current flipzone. This is where price currently IS (or recently was). In many cases during Demand Return, price is already inside this zone. Labeling the flipzone as "TP2" is problematic because it may be at or below the current price for a bull trade.
* eae_secondaryAttractorPrice when UNRESOLVED = inducZoneLow (bull) or inducZoneHigh (bear) — the induction zone. This is typically behind the direction of trade (the zone price came from).
This means the V72 Spec's attractor → TP mapping may be directionally backwards in certain phases. The attractors describe where price needs to return to complete energy resolution, not necessarily where price is going next.
Required correction: The Target Engine must check whether each attractor price is in the direction of the trade before assigning it as a TP level. An attractor below close for a long trade is a support reference, not a target.


// TE must first qualify attractor direction:
bool te_tp1_valid = direction == 1 ? te_tp1 > close : te_tp1 < close
bool te_tp2_valid = direction == 1 ? te_tp2 > close : te_tp2 < close
// If neither is directionally valid → te output = na, doe_action = "Wait"
The FRZ-based target fallback (§8.3) is the more reliable immediate TP source:


// FRZ targets are directionally filtered by frz_dirArr
// Bull trade: highest-score FRZ with direction == 1 ABOVE close = TP candidate
// Bear trade: highest-score FRZ with direction == -1 BELOW close = TP candidate
This FRZ-based TP is safer than attractor-based TP in Phase 1.
Required modifications:
1. Implement FRZ-based TP as the Phase 1 primary TP1 source (directionally filtered).
2. Attractor-based TP is Phase 2 (after attractor directionality is validated).
3. Tertiary attractor (ATR×2.0 extension) is Phase 3 — geometric, must be validated.
4. te_rr_tp1 R:R gate (>= 1.5) is architecturally sound — retain.
5. te_expectedPath derivation is a research hypothesis — implement as display-only, not as decision gate.

ENGINE: INVALIDATION ENGINE (IE2)
Verdict: APPROVED WITH MODIFICATIONS
What is architecturally correct: Invalidation Engine is the most clearly derivable component in the spec. point4OriginLow, point4OriginHigh, flipBot, flipTop all exist in V71 and are the natural stop reference levels. Calculating stop-loss prices before entry is an unambiguous improvement. IE1A already uses close < flipBot - atr * 0.5 for bullInvalid (line 2310) — the Invalidation Engine formalises this.
Flaw — inv_demandFailPrice approximation is wrong: V72 Spec §11.4 calculates demand zone low as:


cycleHigh - (cycleHigh - cycleLow) * 0.60 - atr * 0.10
This is an invented approximation. The actual demand zone in V71 is defined by flipBot (lower boundary of the flip zone). The demand failure price should be:


inv_demandFailPrice = flipBot - atr * bufferMult  // where flipBot is the zone floor
This is directly derivable from existing V71 variables and is not an approximation.
Flaw — inv_supplyFailPrice similarly simplified: Should be flipTop + atr * bufferMult for supply zone top — flipTop exists (line 482).
Required modifications:
1. Replace cycleHigh - (cycleHigh - cycleLow) * 0.60 approximation with flipBot / flipTop directly.
2. Expose ATR buffer multiplier as input (default: 0.25 for origin stops, 0.10 for zone stops).
3. inv_riskInATR is correct and valuable — retain.
4. bullInvalid / bearInvalid at lines 2310–2311 already implement informal invalidation. IE2 must not duplicate this logic — it must read from these existing booleans and extend them with price levels.
5. No conflict with IE1A: IE1A uses bullInvalid/bearInvalid to influence safeToReset. IE2 uses them to calculate and display the price level. Separate authorities, shared input signals.

ENGINE: WAVE REGISTRY (WR)
Verdict: APPROVED WITH MODIFICATIONS
What is architecturally correct: Sequential waveId assignment on wave spawn, parent-child tracking via parallel arrays, and preserving birthBar / deathBar are all achievable in PineScript using var arrays. The spawn hook insertion (at the existing waveReset block, lines ~2041–2064) is clean. No lifecycle logic changes required.
PineScript constraint: PineScript arrays have no struct support. The parallel array approach is correct. However, PineScript does not have a native "find index by value" function — array.indexof() must be used carefully for performance. With a max waveDepth of 4 and limited array growth, this is manageable.
Flaw — wr_activeParentId initialization: When a root wave spawns (isRecursiveWave = false), the parent should be 0 (no parent). When a recursive wave spawns, the parent is the previous wr_activeWaveId. The V72 Spec handles this but the transition logic at wave death needs care: when safeToReset fires (line 2316), wr_activeWaveId resets to 0 before the new wave spawns. The death hook must fire before the reset.
Required modifications:
1. Wave death hook must precede the safeToReset block, not follow it.
2. Array size should be bounded (max 50 entries with rolling eviction) to prevent memory growth on long chart histories.
3. wr_phaseHistory as a comma-separated string is fragile in PineScript (string concatenation per-bar). Store only the phase at spawn and phase at death — not a full per-bar history.

ENGINE: DELIVERY WAVE REGISTRY (DWR)
Verdict: REQUIRES RESEARCH — Defer to Phase 3
What is architecturally correct: The DWR concept is valid. Formalizing delivery wave lineage addresses the Severity 2 audit gap. The spawn conditions (ede_state == 4 transitions) are derivable from existing V71 variables.
Why it must be deferred:
1. The DWR adds significant PineScript complexity (another 6–8 parallel arrays, spawn/death hooks inside state transitions) on top of the Wave Registry — which must be validated first.
2. The downstream consumers of DWR in V72 are: Traceability Framework and Advanced Dashboard only. No decision engine currently consumes DWR output. This means DWR has zero trading impact until further engines are built.
3. The relationship between DeliveryWave and Resolution State needs empirical validation — it is theoretically sound but untested.
Required action: Defer DWR to Phase 3. Implement Wave Registry (WR) first. Once WR is validated and DWR's downstream consumers are defined, implement DWR.

COMPONENT: ERF INTEGRATION FRAMEWORK
Verdict: APPROVED — Implement Phase 1
What is architecturally correct: This is the clearest, most directly derivable addition in the entire spec. The variables are already computed. The gaps are well-defined. The integration is:
1. Surface eae_primaryAttractorPrice as numeric text in dashboard — trivial fix.
2. Add erf_entryGate to longSignal/shortSignal — small addition to lines 2649–2661.
3. Add erf_tradeReadiness as a synthesis of existing RE/EAE variables.
Flaw in erf_entryGate logic: V72 Spec §7.2 allows entry when UNRESOLVED + tradeReadiness >= 60. This means a partially-ready UNRESOLVED state can still produce entries. The logic is:


erf_entryGate = re_resolutionState != "UNRESOLVED" OR (re_resolutionState == "UNRESOLVED" AND erf_tradeReadiness >= 60)
This is equivalent to: erf_tradeReadiness >= 60 OR re_resolutionState != "UNRESOLVED". A high readiness score in an UNRESOLVED state is paradoxical — readiness is partly derived from resolution state. Verify that erf_tradeReadiness can independently reach 60 in UNRESOLVED state without false positives. Simpler and safer:


erf_entryGate = erf_tradeReadiness >= 45  // single threshold, all states
// erf_tradeReadiness naturally scores low when UNRESOLVED (10 pts max from resolution component)
// and high when RESOLVED (40 pts from resolution component)
erf_tradeReadiness double-counting check: The formula (§7.1) uses re_recursiveCompletionScore * 0.25 and erf_confidence * 0.15. erf_confidence (line 1281) includes re_resolutionState as a component. re_recursiveCompletionScore is independent. This is not double-counting — they are separate variables, acceptable.
